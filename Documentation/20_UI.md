# UI del proyecto Saclisam

## Visión general
La UI del proyecto se divide en dos bloques principales:

1. **UI Reactiva** (HUDs y paneles con bindings automáticos).
2. **UI de Combate** (panel de personaje y selección de objetivos).

El objetivo es evitar el polling en `Update()` y centralizar la actualización visual mediante **observables**, eventos y un **controlador de UI** por sistema.

## Arquitectura Simplificada

### Flujo de UI de Combate

```
EventoEncounterIniciado
        ↓
GameFlowController → Push(CombatFlowState)
        ↓
CombatFlowState.Enter()
  ├─ SetContext(InputContext.Combat)            [GameInputManager]
  └─ CombatUIController.MostrarHUD()            [visibilidad]
        ↓
HUDController.MostrarHUD()  →  display: Flex  (el HUD aparece)
        ↓
EventoCombateIniciado
  ├─ CombatUIController: isInCombat = true      [solo flag]
  └─ HUDController: PopularTurnOrder()          [solo datos]
        ↓
EventoEsperandoAccionJugador
  ├─ CombatUIController: ShowHighlight,  state → ShowingCharacterPanel
  └─ HUDController: MostrarPersonaje (info + botones dinámicos)
        ↓
Click en habilidad → EventoAccionSeleccionada
        ↓
CombatUIController: ShowTargetSelector (si requiere objetivo)
        ↓
Click sobre enemigo/aliado en escena → EventoObjetivoSeleccionado
        ↓
CombateManager ejecuta la acción
        ↓
EventoCombateFinalizado          (o → siguiente turno)
  ├─ CombatUIController: limpia highlight/selector
  └─ HUDController: limpia datos internos
        ↓
GameFlowController → Pop()
        ↓
CombatFlowState.Exit()
  └─ CombatUIController.OcultarHUD() → HUDController.OcultarHUD()
        ↓
display: None  (el HUD desaparece)
        ↓
ExplorationFlowState.Enter() → SetContext(InputContext.Exploration)
```

> **Regla de oro**: La **visibilidad** del HUD la controla **exclusivamente** el
> `GameFlowController` a través de la cadena:
> `CombatFlowState` → `CombatUIController` → `HUDController`.
> Los event handlers de `EventoCombateIniciado`/`EventoCombateFinalizado`
> dentro de `HUDController` y `CombatUIController` solo gestionan **datos y flags**,
> nunca llaman a `MostrarHUD()` / `OcultarHUD()`.
>
> El cambio de contexto de input es responsabilidad del `GameFlowController`
> a través de los estados `CombatFlowState` / `ExplorationFlowState`.
> Ver [29_Stack_FlowController](29_Stack_FlowController.md).

## 3) UI de Combate

### CombatUIController
**Archivo:** `Assets/Scripts/UI/Combat/CombatUIController.cs`

**Responsabilidad:**
- Singleton coordinador de UI de combate.
- Escucha eventos del `EventBus` para gestionar **estado y datos** (no visibilidad).
- Gestiona highlight del personaje activo.
- Controla el `TargetSelector`.
- **Punto de entrada único** para mostrar/ocultar el HUD, llamado desde `CombatFlowState`.

**Eventos escuchados:**
- `EventoCombateIniciado` → `isInCombat = true` (solo flag, sin tocar visibilidad)
- `EventoCombateFinalizado` → `isInCombat = false`, limpia highlight/selector (sin ocultar HUD)
- `EventoEsperandoAccionJugador` → Muestra highlight, guarda aliados/enemigos
- `EventoTurnoFinalizado` → Limpia highlight/selector, mantiene HUD visible entre turnos
- `EventoAccionSeleccionada` → Muestra TargetSelector si la habilidad requiere objetivo

**Métodos públicos (usados por CombatFlowState):**
- `MostrarHUD()` → Delega a `HUDController.MostrarHUD()`
- `OcultarHUD()` → Delega a `HUDController.OcultarHUD()` + limpia highlights

**Estados (`CombatUIState`):**
- `Hidden` — UI oculta (fuera de combate)
- `ShowingCharacterPanel` — HUD visible con info de personaje y botones
- `SelectingTarget` — Seleccionando objetivo para una habilidad

### HUDController (UI Toolkit)
**Archivo:** `Assets/Scripts/UI/Combat/HUDController.cs`
**Layout:** `Assets/UI_Toolkit/HUD.uxml` + `HUD.uss`

**Responsabilidad:**
- Renderiza el HUD de combate usando UI Toolkit (`UIDocument`).
- **No controla su propia visibilidad.** Solo responde a `MostrarHUD()` / `OcultarHUD()`
  llamados por `CombatUIController`.
- Escucha eventos del `EventBus` para poblar **datos** (TurnOrder, info de personaje).

**Componentes visuales (UXML):**
- TurnOrder (panel de orden de turnos, arriba-izquierda)
- Panel de personaje: imagen, nombre, nivel, barras vida/mana
- Botones de acción: Habilidades, Usar Item, Defencerce
- Panel dinámico de habilidades (`AbilitiesDinamicHolder`)
- Botón de refuerzos (visible solo si `HayRefuerzosDisponibles()`)
- Botón MainMenu (placeholder para futuro menú)

**Eventos escuchados:**
- `EventoCombateIniciado` → `PopularTurnOrder()` (solo datos, no visibilidad)
- `EventoCombateFinalizado` → Limpia datos internos (no oculta el HUD)
- `EventoEsperandoAccionJugador` → `MostrarPersonaje()` con info/botones
- `EventoTurnoFinalizado` → Limpia botones, desactiva acciones

**Flujo interno:**
1. Click en personaje → `MostrarPersonaje(entity)`
2. Si es su turno → Botones habilitados (`ActualizarEstadoBotones`)
3. Habilidades generadas con `AbilitySlotFactory.Crear()` → slots ricos (nombre, categoría, costo, efecto)
4. Click en habilidad → `EventoAccionSeleccionada`
5. "Defender" → `EventoObjetivoSeleccionado` (self-target directo)

**Instrucción de objetivo:**
- `MostrarInstruccionObjetivo(string)` crea/muestra un `Label` con clase `.target-instruction`
  dentro del root del HUD. Reemplaza al antiguo panel uGUI de `TargetSelector`.
- Se llama desde `CombatUIController.ShowTargetSelector()` y se oculta con `HideTargetSelector()`.

**Visibilidad por defecto:**
- El USS define `.hud-root { display: none; }` como defensa.
- `OnEnable()` refuerza con inline `display: None`.
- Solo `MostrarHUD()` lo cambia a `display: Flex`.

### AbilitySlotFactory
**Archivo:** `Assets/Scripts/UI/Combat/AbilitySlotFactory.cs`

**Responsabilidad:**
- Factory estática que genera un `VisualElement` completo por cada `HabilidadData`.
- Cada slot (`.ability-slot`) contiene:
  - **Header:** nombre (`.ability-slot__name`) + badge de categoría (`.ability-slot__category`)
  - **Detalle:** tipo de objetivo (`.ability-slot__target`) + costo (`.ability-slot__cost`) + efecto principal (`.ability-slot__effect`)
- Recibe `bool disponible` para aplicar `.ability-slot--disabled` y deshabilitar el click.
- Colores de categoría por USS: `.cat--atk`, `.cat--heal`, `.cat--buff`, `.cat--debuff`, `.cat--cc`, `.cat--util`.

**Método principal:**
```csharp
static VisualElement Crear(HabilidadData hab, bool disponible, Action<HabilidadData> onClick)
```

**Helpers internos:** `DescribirCategoria`, `DescribirObjetivo`, `DescribirEfectos`, `ObtenerElementoPrincipal`, `ClaseCategoria`.

### TargetSelector
**Archivo:** `Assets/Scripts/UI/Combat/TargetSelector.cs`

**Función:**
- Crea indicadores 3D (prefabs) sobre los objetivos válidos durante la selección.
- Se conecta con `IsometricCameraController` para detectar hover por raycast.
- Colorea indicadores según tipo: aliado (verde), enemigo (rojo), seleccionado (amarillo).
- **Sin dependencias uGUI**: toda la UI textual (instrucciones) se delega a
  `HUDController.MostrarInstruccionObjetivo()`.

**API:**
```csharp
void Show(HabilidadData skill, List<IEntidadCombate> allies, List<IEntidadCombate> enemies)
void Hide()
bool IsValidTarget(IEntidadCombate target)
```

- `CombatUIController.ShowTargetSelector()` llama a `Show()` y genera
  el texto de instrucción vía `HUDController`.
- `CombatUIController.HideTargetSelector()` llama a `Hide()` y limpia el texto.

## 5) Cómo configurar en Unity

### Jerarquía recomendada:
```
Scene Root
├── GameFlowController (MonoBehaviour, singleton)
├── CombatUIController (MonoBehaviour, singleton)
│       SerializeField: hudController, targetSelector, playerTurnHighlightPrefab
├── HUD_UIDocument (GameObject)
│   ├── UIDocument        (con HUD.uxml asignado)
│   └── HUDController.cs  (RequireComponent UIDocument)
└── TargetSelector (indicadores 3D sobre objetivos)
```

### Inspector de CombatUIController:
- `hudController` → Referencia a HUDController (auto-buscado si no se asigna)
- `targetSelector` → Referencia a TargetSelector
- `playerTurnHighlightPrefab` → Prefab de highlight

### Inspector de HUDController (UIDocument):
- El UIDocument debe tener asignado `HUD.uxml`.
- No requiere configuración manual en el Inspector; todo se bindea por nombre
  de elemento UXML en `OnEnable()` (`BindElements`, `BindButtons`).

## 8) Notas de implementación

### Control de visibilidad del HUD
La visibilidad del HUD la controla **únicamente** la cadena:
`GameFlowController` → `CombatFlowState` → `CombatUIController` → `HUDController`.

- `HUDController` **nunca** llama a `MostrarHUD()` / `OcultarHUD()` en sus
  propios event handlers (`OnCombateIniciado`, `OnCombateFinalizado`).
- El USS define `.hud-root { display: none; }` y `OnEnable()` refuerza con
  inline style para garantizar que el HUD arranque oculto.
- Esto evita el bug donde el HUD quedaba visible todo el tiempo porque
  `EventoCombateIniciado` lo mostraba independientemente del GameFlow.

### Botón de Refuerzos
Solo aparece si `PlayerPartyManager.Instance.HayRefuerzosDisponibles()` retorna `true`.
Esto significa que hay personajes estacionados que pueden unirse al combate.

### Panel de Habilidades (AbilitySlotFactory)
Se genera dinámicamente en `HUDController.GenerarBotonesHabilidades()` usando
`AbilitySlotFactory.Crear()` por cada `HabilidadData` del personaje activo.
Cada slot muestra:
- Nombre + badge de categoría (Ataque, Curación, Buff, Debuff, CC, Utilidad)
- Tipo de objetivo + costo de mana + efecto principal
- Estado visual: disponible o deshabilitado (`.ability-slot--disabled`)

### Target Selection (indicadores 3D + instrucción UI Toolkit)
`TargetSelector` crea indicadores 3D (prefabs) sobre los objetivos válidos.
La instrucción textual ("Selecciona un enemigo", etc.) se muestra como
`Label` dinámico en el HUD vía `HUDController.MostrarInstruccionObjetivo()`.
`CombatUIController` gestiona la lógica de confirmación en `OnEnemyClicked`
/ `OnAllyClicked` y orquesta tanto el `TargetSelector` como la instrucción.

### Entre turnos
`OnTurnEnded` **no** oculta el HUD (ya no pone `CombatUIState.Hidden`).
El HUD permanece visible durante todo el combate, solo se limpian
highlights y el selector de objetivo.

### Buffs/Debuffs
Los contenedores están preparados pero la lógica de mostrar iconos
está pendiente de integración con el sistema de estados.
